# ScreenerPro (SmartMoneyBOS)

Long-only daily **crypto investment advisor webapp**. Fully static — no build step, no deps.

## Files
- Chart tab opens on **ARBUSDT · 4h · 4500 bars · liqbrk** (user's default combo; TF moved 2h→4h Oct 2026, when the 2h alerts were dropped) — the same coin and TF the signal bot watches.
- `index.html` — UI: four tabs (**Portfolio** = the default home screen / **Alerts** / Chart / **Compare** — all strategies × a user-editable symbol list), strategy dropdown, Advisor panel, equity backtest, mobile-first: the Portfolio screen's phone styles are the BASE, a `@media(min-width:700px)` block upgrades it to multi-column, and a fixed bottom tab bar replaces the header nav under 700px. All media queries stay at the END of `<style>` so they win the cascade. Fetches Binance spot klines client-side (`api.binance.com`, fallback `data-api.binance.vision`).
- **Fetch by bars OR by date range** (Oct 2026, both tabs): `#rangeMode` / `#cmpRangeMode` switch between a bar count and `From`/`To` date inputs. `fetchKlines(sym, tf, spec, onPage)` takes `spec` as either a bar COUNT (number) or a RANGE (`{from,to}` in ms) — in range mode it pages back until it passes `from` **or the pair's history runs out**, so a start date older than the listing silently yields the earliest bars that exist. That clamp is always reported, never hidden: the Chart status reads `… · SOLUSDT only lists from 2020-08-11`, and Compare collects them into `short[]` → `listed later, clamped to earliest: SOL from 2020-08-11, AVAX from 2020-09-22`. **Rows clamped this way cover less history than their neighbours — the Yrs column is what makes two rows comparable.** In date mode Compare still needs the 10k reference, so it fetches back to `min(from, to − CMP_REF_BARS × TF_MS[tf])` and slices both windows out of the one result. `cmpRowKey()` is the single source of the row-cache key for both modes — never rebuild it inline, that is how `renderCmp` and `runCompare` once read different keys.
- `runCompare` **queues** a request that arrives while one is in flight (`cmpPending`) instead of dropping it. Dropping it left the table rendering a key nobody had computed — reachable by switching to date mode (which fires a fetch) and then picking dates a moment later.
- **Compare tab** (Sep 2026): timeframes **15m/1h/2h/4h/1d/1w** (15m added Oct 2026). It **opens on All strategies · 4h · 19,096 bars (≈8.7 years) with Window sweep on**, the user's own settings (Oct 2026): `#cmpStrat` defaults to `all`, `CMP_BARS['4h']` = 19096, and 15m starts at 35,040 bars (≈1 year, 36 pages a coin, the heaviest pull this tab makes). Symbol list is editable (`#cmpSyms`, comma-separated, bare tickers get `USDT` appended, persisted in `localStorage` under `smb.cmpSyms`, `Reset list` restores `CMP_DEFAULT`). **`CMP_DEFAULT` is the user's own 103-coin list (Oct 2026), in their order.** XMR (data ends 2024-02-20) and LIT (Litentry, ends 2025-02-10) are delisted, so their rows grade history only up to the delisting. A fresh browser opening Compare therefore starts a 103-coin run that takes minutes, not seconds; browser tests set a short `smb.cmpSyms` first; unreachable/delisted symbols are named in `#cmpStatus` rather than silently dropped. **Bar count is user-set** (`#cmpBars`, 300–60000, persisted under `smb.cmpBars`, live "≈ N days/mo/yrs" readout in `#cmpSpan` that turns red under 200 days): it tracks `CMP_BARS[tf]` until the user types a number, then stays pinned across TF changes (`cmpBarsTouched`). `cmpCache` is keyed `sym|tf` storing `{rows, asked}` so lowering the count slices what is already held instead of refetching, and a symbol with genuinely short history is not refetched forever; `cmpRowsTf` is keyed `tf|bars`. The 300 floor exists because `runCompare` skips anything under 250 bars — don't lower it or the box can select a guaranteed-empty table. `#cmpStrat` options are **generated from `CMP_STRATS`** — never hand-write them again, that is how `composite`/`meanrev` survived their July 2026 removal as dead options. **Window sweep** (`#cmpSweep`, on by default) slides a window of 35% of history across the equity path inside `pathStats` — no extra engine runs, no extra fetches, so toggling it is a pure re-render. **Every run measures TWO windows**: the user's bar count *and* a fixed `CMP_REF_BARS`=10,000 reference, both sliced from one fetch (`need = max(bars, 10000)`) so the reference costs no extra requests — which also means raising the Bars box anywhere below 10,000 never refetches. Rows carry `{e:recent, d:reference, sameWin}`. **`#cmpPick`** renders the go-to combo above the table: it requires the FULL investment test (`okRow`, shared with the table's ✓) on the **reference**, plus only a form check on the recent window (`n>=3 && net>0 && edge>0`) — a short window cannot carry the trade floor when `liqbrk` takes ~7 trades/year on 4h, so demanding it there would fail every window on arithmetic rather than merit. Ranked by **reference** edge, never the noisy recent one. The panel is a hero figure + KPI rows (not a chart — it is a handful of headline numbers for one pick), states the timeframe, mutes any stat from a window below `minTrades()` with a `*`, and must keep its two caveats: the windows **overlap** (recent sits inside the reference, so it is not two independent tests) and everything is a backtest. When nothing qualifies it says so and names the closest miss — never invent a pick.
Columns (Oct 2026, rebuilt for investment comparison — CAGR/6M/1Y/Sharpe removed): Vol · Trades · **Net P/L** · **vs B&H** · PF · Max DD · Win rate · **In mkt** · Stable · Yrs · ✓. **✓ is sortable** (`data-k="ok"`): ticked rows first, each group ordered by vs B&H; a second click reverses. `vs B&H` = `(1+net)/(1+bh)−1`, how much richer you ended than holding the same coin over the same window. ✓ requires `net>0 AND edge>0 AND PF≥1.3 AND WR≥30% AND DD≤60% AND closed trades ≥ `minTrades()` — **12 on 1h and below, 20 above** (user decision Oct 2026, was 30; see ALGORITHM.md for the noise this accepts) AND ≥70% of windows profitable`. On 1h only `liqbrk` produces a real sample (Cycle needs a 200-week MA; Trend/Turtle need months per trade), which is why those rows show 0–2 trades.
- **Top 100 button** (`#cmpTop100`, Compare) fills the symbol list with the 100 largest coins **by market cap that trade on Binance spot**. Ranking from CoinGecko `/coins/markets` (keyless, CORS-open, 250 fetched so 100 survive filtering); tradability from Binance `/ticker/24hr?type=MINI` — a pair must have traded in the last 24h, because Compare fetches Binance klines and anything else is just a skipped row. Excluded on purpose: stablecoins (any base containing `USD`, plus `NOT_COIN_SET`) — not investments, and they wreck every return stat; wrapped/staked/restaked/bridged copies (`NOT_COIN_NAME`) — WBTC/stETH are BTC/ETH again; tokenised gold; leveraged UP/DOWN/BULL/BEAR tokens; and any base that would not survive the `cmpSymsText`→`parseSyms` round trip. Duplicate tickers keep the higher-cap coin. **If CoinGecko fails, the list is ranked by Binance 24h volume and the confirm AND the persistent status line say so** (`cmpListNote`) — never pass volume off as market cap. **Ranked fresh on every click** (Oct 2026: a 24h cache made repeat clicks look hardcoded). `smb.top100` keeps the last good list only for when Binance can't be reached, and then the confirm and status line say how old it is. **Top 50 gainers** (`#cmpGainers`, Oct 2026) is Binance's own 24h ranking of USDT spot pairs (`/ticker/24hr?type=MINI`, `lastPrice/openPrice − 1`), also fetched fresh on every click. It adds a $1M 24h-volume floor (`GAIN_MIN_VOL`). Both buttons REPLACE the symbol list, and their confirm says so. **Both lists take NORMAL SPOT COINS only** (`isNormalCoin()`, user request Oct 2026). Binance spot also trades ~100 **tokenized stocks and ETFs** (AAPLB, NVDAB, SPYB, and leveraged/inverse ETF tokens like TQQQB, SQQQB, SOXLB, UVXYB). On live data the first gainers build took 12 of them into the top 50, and the volume fallback took 18. `spotUniverse()` reads two lists fresh on every click. The first is `exchangeInfo?permissions=SPOT&symbolStatus=TRADING&showPermissionSets=false`, Binance's currently-trading pairs (~55 KB gzipped). Every leveraged token (BTCUP, ETHDOWN, ETHBULL, …) is delisted (BREAK), so this list already drops them. The second is `permissions=TRD_GRP_261`, Binance's own trading group for the stock tokens (~4 KB; real coins sit in TRD_GRP_258). **Never filter these by name.** Real coins end in B (ARB, BNB, SHIB, CKB, DGB, TRB, BB, YB) and in UP (JUP, SYRUP), and stock tokens collide with crypto tickers (STXB is Seagate, not Stacks; BBB is BlackBerry, not BounceBit). If the group list can't be read, or stops looking like stock tokens (under 20 entries, or a name not ending in B), `STOCK_SNAPSHOT` (the 100 of Oct 2026) stands in. If the trading list can't be read, `isLevToken()` stands in: prefix + UP/DOWN/BULL/BEAR, where the prefix must itself be a listed coin. The status line (`coinsNote`) says when either fallback was used. A `confirm()` states the upper-bound cost first (`cmpEstimate`: pages × ~0.3 s ÷ 3 + `CMP_CPU_S` per coin). **Big lists change how `runCompare` runs**: over 12 symbols it keeps **3 coins in flight** (network overlaps compute; `fetchKlines` already backs off on 429/418, and 3 × ~5 req/s is far inside Binance's 6000-weight/min); up to 12 it is the old one-at-a-time path, unchanged. Over 25 symbols each coin's raw candles are **evicted from `cmpCache` once its rows are computed** — 100 coins × 20k bars is ~2M candle objects, enough to kill a phone tab; the rows are all the table needs, and changing Bars simply refetches. Measured with mocks on 4h: 100 coins, 400 rows, ~1,500 requests, never more than 3 in flight, 37 MB heap.
- **Portfolio tab** (`#pfView`, the default view): driven by an **orders ledger** — `localStorage` `smb.orders` = `[{id,sym,side:'buy'|'sell'|'open',qty,price,time,src}]`, **never committed, never uploaded**; don't hardcode anyone's positions into the repo. Holdings are DERIVED by `replay()`, oldest order first, **average-cost** method (buy blends the average, sell realises `(price−avg)×qty` and leaves the average alone, sold-to-zero resets it); fees are not modelled. A sell beyond the recorded buys realises only what is accounted for and is flagged (`short`), never given an invented cost. `side:'open'` is an **opening-balance snapshot** (the old typed-in holdings, migrated once from `smb.holdings`, which is left untouched): it SETS the position at its time and supersedes that coin's older orders, so imported history can never double-count a hand-typed balance; the screenshot importer offers to replace it, ticked by default. Hero = live value; KPI row = unrealised P/L (+ realised in its subline) / cost basis / best-worst mover / **BTC regime**. **Loading is shown loudly** (Oct 2026, user request; the grey "loading 4h… 12/62" text was easy to miss). `#pfLoadBar` is a green 5px bar fixed to the top edge. It sits inside `#pfView`, so other tabs hide it; it slides while `bkLoad` reads the book, then fills done/total as prices load. A green `.pfLoadPill` in `#pfAsOf` carries the count. `pfProgress(label, done, total)` drives both, and `pfProgress(null)` finishes them. `pfRun` ends in `try/finally`, so the bar always clears and `pfBusy` always resets; with no prices loaded, the heading says so. Each holding card carries price, 24h, worth-now, what-you-paid, P/L **and an action line** from `actionFor()`. The **Holdings & orders** panel lists every coin (sold-out ones too) with its orders, add-order form, **screenshot import**, and backup/restore (download/upload JSON — the ledger lives in one browser, so clearing site data loses it). **Screenshot import** runs Tesseract.js **in the browser** — screenshots never leave the device; only the engine downloads (~6 MB, once). Versions are **pinned** in `OCR` (tesseract.js 5.1.1 / core 5.1.1 / eng data 1.0.0) — don't float them, a CDN release could silently change what is extracted. `prepImage()` greys, inverts dark screenshots and stretches contrast. `parseOrdersText()` anchors on a pair that **leads its line** (that is what stops `Total 19.50 USDT` becoming a coin called "50"), strips OCR's stray I/J/L/1 at the slash (`ARBI/USDT`), skips cancelled orders, and uses **Total as a cross-check** — qty×price must equal it, and a mismatch is corrected toward the digit-subset reading and FLAGGED. **Nothing reaches the ledger without the review screen**: anything flagged, repeated across screenshots, or matching an existing order is left unticked. The parser was tuned on synthetic Binance-style screenshots (order-history and trade-history layouts); real app layouts may differ, which is exactly what the review step and "What the reader saw" are for. **The trading book** (`#bookBox`, Oct 2026, replaced the old "system track record" backtest panel, `PF_CORE` and `renderBacktest` — user decision) is the guider: capital box (`smb.bookCapital`, **browser only, never in the repo**), tiles for book value / in trades / idle USDT / next slot size, a 5-slot strip, **Did you buy it?** cards for alerted-but-unanswered signals, and the full journal with filters. **Journal rows open their chart** (Oct 2026, user request): `openJournalChart(e)` uses the row's coin, timeframe and strategy. It switches to Bars mode with enough bars to reach past the entry, then zooms to the trade from 60 bars before entry to 25 after exit (or now). Clicks on the row's Took it / Skip buttons only answer. Every "open this coin's chart" path (journal rows, holding cards, Compare rows) goes through `chartRun()`. `showView('chart')` already runs the first load, so the old `showView('chart'); run()` fetched the coin twice on a first open. It reads `signals/book.json`, `journal.json`, `decisions.json` and `watchlist.json` through `ghReadJSON` (Contents API, raw CDN fallback flagged stale). `bkReplay(cap)` sizes **Taken** entries only, each at `min(cash, book-at-cost ÷ slots)`, with the +3R half and 0.1%/side fees, and a dropped entry returns at cost. `bkHolds` must mirror the bot's `holds` exactly (open/half AND (taken OR alerted & unanswered)), or the strip and the bot disagree on free slots. `bkDecide` saves to `smb.bookLocal` at once. With `smb.ghToken` it then GETs decisions.json, merges and PUTs it. Without a token it opens `#bkManual` with the merged file to paste, because **the tokenless route must always work**. Local answers drop once the repo confirms them. "On the radar" = the **top 5 alert-list coins closest to a buy** (conditions met, then gap to the breakout), excluding coins you hold, coins with an open book entry and coins with an open strategy trade. The regime tile reads **BTC's** 200-day MA.

- `scripts/signal-bot.js` + `.github/workflows/signals.yml` — **out-of-browser buy/sell alerts.** Runs the same `detector.js` against fresh klines on a cron (**every 15 min** — the old 2-hourly schedule actually fired every 5–6h because GitHub delays/drops scheduled runs; README "Punctual alerts" shows an outside trigger for exact timing), and pushes only on a position FLIP. Two invariants: it **drops the forming candle** (`closeTime <= now`) so an alert never refers to a bar that can still change — the webapp deliberately keeps that bar, the bot must not — and it persists position state in `signals/state.json`, committed back by the workflow, so each flip fires once. **No open position is ever silent:** on a first sighting an entry on a candle closed after the previous persisted run (`state._meta.lastRun`, written only with a real change) is a normal BUY, an older one gets ONE `OPEN TRADE` note (levels + whether price is still within 1R); state's `noted` marks a position as announced, and positions recorded silently before notes existed get theirs on the next run. Closed history before you watched stays quiet. A state entry **older than 10 bars re-baselines silently** instead of alerting — otherwise removing a coin and re-adding it weeks later would announce a trade that opened, and maybe closed, while nobody was watching. Watchlist is data (`signals/watchlist.json`), not code. **Trading book (Oct 2026, user decision, ALGORITHM.md "The trading book"):** 5 equal slots (`signals/book.json`). Every signal, taken or not, is recorded in `signals/journal.json`, which the workflow commits with state (rebase-retry push). The user's Taken/Skipped answers are `signals/decisions.json`, written by the page; ids are `SYMBOL|tf|entryBarTime`. Nothing is sent inside the item loop: events are queued, then handled in phases. Order: sells/halves → rules notes → buys/opens, highest relative volume first → deferred halves → late entries for every open position without one → entries whose coin left the watchlist become `dropped`. A slot is held by Taken, or by alerted & unanswered. When all are held, a BUY is **journal-only, no alert**. An OPEN TRADE note needs a free slot AND price within 1R. SELL/TAKE HALF alert only for a held trade. **The repo never holds money amounts.** `--book/--journal/--decisions` (like `--state/--watch`) redirect the files for tests. Channels are additive and all optional (ntfy / Telegram / Discord), with a GitHub issue as the zero-setup fallback, which fires ONLY when no other channel is configured (otherwise every signal leaves a ticket to close). `--dry-run`, `--selftest` and `--fixture <path>` run it without a live market; `--fixture` is how the buy/sell transitions are tested. `--ping` (also a `workflow_dispatch` input) sends a test message through every configured channel and exits — the only way to verify a channel without waiting for a real trade; note `dry_run` sends nothing, so it is the wrong switch for that. **Secrets never go in `index.html`** — the page is public, so a bot token in client code is a token anyone owns; that is why alerts are sent from the workflow and not the browser. Setup and caveats in `signals/README.md`.
- **Alerts tab** (`#alView`, 4th tab) — edits `signals/watchlist.json`, the file the Action reads, from the phone. The page is static with no backend, so it cannot write to the repo alone; two routes exist and **the tokenless one must always work**: copy the JSON into GitHub's web editor, or save a fine-grained PAT in `localStorage` (`smb.ghToken`) and let Apply commit via the Contents API. A token is **never** written into the page or the repo — same rule as the bot secrets. The live list is re-fetched on EVERY visit to the tab via the **Contents API** (`raw.githubusercontent.com` is only the fallback and is flagged "may be up to 5 min old" — its CDN ignores cache-busters, which once left a just-committed list showing its old rows struck through), never assumed from local state. **A draft records the live list it started from (`smb.alBase`)**: if the repo moved on since, an unedited draft is dropped and an edited one raises a "draft is older than the bot's list" banner with Apply blocked until the user picks — Oct 2026 a stale phone draft committed through the web editor silently reverted 19 alerts. Drafts are deleted whenever they equal the live list, and the banner says `In sync` / `Not applied yet` with an add+remove count: a silent divergence would mean editing a list the bot has never seen. Removals render struck-through with an undo. Draft is `smb.alDraft`; owner/repo is derived from the Pages hostname, overridable via `smb.alRepo`.

## Strategies (dropdown → `strategy` param)
- `cycle` (default) — BTC halving playbook: staged accumulation at the 200-week MA (zone A + deep zone B, harmonic avg entry, stop 0.65×200w), Pi-Cycle / 40-week exits. **Rebuilt Oct 2026** (ALGORITHM.md top of the cycle section; study `research/cycle/RESULTS_cycle_2026-10.md`). The old code bought alts with the stop ABOVE the price and "sold" at that stop the next bar, above the whole candle. ADA 4h showed 60 trades, 49 impossible, $1k → $724M; the median over 209 coins was +7.5 million %. It lives in `runCycle()`, outside `runQuant`'s bar loop, and is a **daily system on every chart**: `dailyBars()` aggregates sub-daily candles to UTC days and the trades are mapped back onto the chart's bars, so 4h and 1d give identical trade dates. Don't move it back into the per-bar loop, where "5 days under the 40w" was counted in bars and one 4h close reset it. Rules: the stop is checked on the day's low BEFORE any tranche buy and fills at `min(open, stop)`; zone entries and tranche 2 need price ≥ 0.72×200w. **Alts follow BTC's cycle** through `params.btcD`, BTC DAILY candles with all history (the app's `btcDailyFor()`, ~4 pages, shared, 5-min refresh; `'self'` on BTCUSDT, where gating is a no-op). Without BTC data the gate is open and `advice.cycle.btc.missing` is set; the status line and advisor SAY so. Half is sold at the first close ≥ `cycleScale` (1.85) × the 200-day MA, never below the entry. Trades carry `fills` [{idx,w,px}], and `SMC.markMult` floats only the tranches filled by bar j, so drawdown isn't overstated before later tranches. `research/cycle/cycle_lab.js parity` checks the lab against the pre-rebuild engine (from git); `parity-final` checks it against today's engine (209/209 on 1d, 44/44 on 4h). Run both before touching the cycle. Honest result: the median alt still loses −7% at a −67% drawdown, against −85% / −98% for holding. It is a BTC playbook alts can borrow, not an alt picker.
- `tsmom`, `donch` — pure CTA trend / turtle breakout.
- `liqbrk` — **buy-side liquidity continuation**. **Oct 2026 (user-approved, ALGORITHM.md top of the liqbrk section): entries also need BTC above its 50-day MA OR the coin +50% over 30 days (`lbBtcMaDays` 50 / `lbLeadPump` 0.5), and half the position is sold at entry + 3R (`lbScaleR` 3); 149 MA kept.** The gate needs a BTC series in `params.btc` — the app's `btcFor(tf, c, sym)` (shared 5-min cache per TF, 51 days of warm-up) and the bot's `btcFor` supply it; without one the engine opens the gate and flags `advice.lb.btcGate.missing`, and the app/bot SAY so (the bot skips the item). A scaled trade stays ONE record: `exitPrice` = weighted average of both halves, `scale = {idx, px, w}`, `exitRest` = the second fill; every equity path must mark it with `SMC.markMult(t, j, close)` or drawdown is overstated. `research/liqbrk_lab.js parity` checks core AND shipped rules trade-for-trade; `pytester` models the core rules only (verify passes the new features off). Coins watched on BOTH 2h and 4h get paired BUY messages — 2h `(heads-up)`, 4h `(trade)` with a confirmed/unconfirmed line (`pairLine`, measured Oct 2026: 42% of 2h buys become a 4h buy within 24h); items run 2h-before-4h so the 4h item reads the 2h `lastEntry` from state. The bot's state carries `rules`; `RULES` in signal-bot.js is **per strategy** (`RULES[strat]`, Oct 2026). Bump only the changed strategy's entry so its positions re-baseline with one "Rules updated" note instead of a fake BUY/SELL; a single global string would make every liqbrk alert re-baseline over a cycle change. Cycle alerts get BTC daily (`btcD`) and act on **finished UTC days only**, because the bot never alerts on a candle that can still change and for the cycle that candle is the day. Their messages say the cycle's own rules (sell zone, 40-week exit, tranche program). Runs on 15m but is a **SWING system** (holds ~30h, ~6 trades/mo) — do not call it intraday. First close above the 2-day high + above the 5-day SMA + above the **149-bar MA of the selected chart TF** (`lbMaBars`, bar-native by design — the one documented exception to day-denomination; 0 = off) + volume ≥1.3× its daily average → long; stop 3×ATR; trail out below the 1-day low. The 149 MA gates entries only, and every benchmark below predates it. Edge is the MECHANISM (plateau across every param), not a threshold. **`lbBrkExt` (Sep 2026, DEFAULT 1.0 — ON; `lbStop` also 3→4)** additionally requires the close to clear the 2-day high by ≥n×ATR; at 1.0 it lifts WR 30.2→35.6% and PF 1.10→1.33 on a 10-symbol 1h study, but is **not ZEC-validated** — run `pytester/liqbrk_v2_test.py` first. Two further wins measured but NOT shipped (no book-level state in the app): a BTC-momentum veto that turns 2022 positive, and a max-5-concurrent cap that halves drawdown. See ALGORITHM.md. ZEC 15m **full history** (258k bars, 2019-2026): WR 24%, PF 1.39, +199%, maxDD **61%**, 15/31 losing quarters, and it loses for ~2.5 years through the 2022-24 bear. The often-quoted WR 34% / maxDD 13.5% came from a 2-year bull window only — see the CORRECTION in ALGORITHM.md. Treat it as a bull-regime system.

## Conventions
- Run locally: `python -m http.server 8910` (or preview config `bos-backtester` in `.claude/launch.json`).
- Benchmarks: Node scripts that `require('./detector.js')`, fetch Binance daily klines, compute all-in equity with 0.1%/side fees, marked-to-market daily drawdown. Always compare vs buy & hold and report WR/DD/CAGR per symbol.
- The user judges strategies by: win rate ≥30%, drawdown, consistency across ≥5 symbols. Don't overfit weak assets (XRP/LINK fail deliberately).
- Equity panel is exposure-based (`Invest %` of equity per hold, 100% = all-in), NOT risk-per-trade sizing.
- If a rule changes, change `ALGORITHM.md` first.
- **Validate on ALL available history, not the cached window.** ZEC 15m reaches back to 2019-03-21 (~258k bars). A 2-year bull slice made `liqbrk` look like a 13.5%-drawdown system when it is really a 61%-drawdown one.
- **There is NO Binance bar-count ceiling.** `fetchKlines` pages backwards via `endTime`, so depth is limited only by the pair's listing date — BTCUSDT 4h reaches 2017-08-17 (19,959 bars, **9.1 years, two halving cycles**). The old `10000` was a self-imposed `max=` on the Bars inputs; a code comment mistook it for an API limit and that error propagated into ALGORITHM.md. Both inputs now allow 60,000. **This mistake cost real accuracy:** the 4.6-year 4h window reported BTC's `liqbrk` drawdown as −14% when over two cycles it is **−39%** (BNB −19%→−38%, DOGE −39%→−74%). Always quote the deep-window drawdown. Encouragingly, window *stability* held or improved on 7 of 10 symbols over two cycles — the short window flattered risk, not the edge.
- **A robust edge is not the same as a worthwhile one — always check `vs B&H`.** Over 9.1 years on 4h, `liqbrk` on BTC returned +837% while holding BTC returned ~+1,800%: trading halved the outcome. Same on LINK/BNB/SOL. The Sep 2026 "BTC is the best symbol" conclusion tested robustness of the edge and never asked whether it beat the asset.
